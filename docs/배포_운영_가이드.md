# Windows 클라이언트 배포 운영 가이드

## 표준화 기준

- Windows x64와 PowerShell 7.2 이상에서 실행한다. SDK는 [global.json](../global.json)의 고정 버전이다.
- 릴리스 버전과 Velopack NuGet 버전은 [클라이언트 프로젝트](../src/LabPet.Client/LabPet.Client.csproj)에서 관리한다. 태그는 프로젝트 버전에 `v`를 붙인 값이며 패키지 ID, RID, 실행 파일명은 [공통 스크립트](../scripts/Common.ps1)에 정의한다. 빌드에서 Velopack CLI의 설치 버전을 NuGet 버전과 비교한다.
- Windows 클라이언트 배포는 [GitHub Releases](https://github.com/DJU-ADAS-LAB/LabPet/releases)와 Velopack 정적 업데이트 피드를 사용한다. Windows 패키지는 앱, .NET 런타임 및 7종 캐릭터 리소스를 포함한다. GCP SignalR 중계는 별도의 서비스다. [GCP 서버 배포와 운영](../deploy/gcp/README.md)

## 로컬 검증

저장소 루트에서 실행한다. 출력 디렉터리는 비어 있어야 한다. 기본 출력은 Git에서 제외되는 `.artifacts/` 아래에 생성한다.

```powershell
pwsh -NoProfile -File scripts/Verify.ps1 -OutputDirectory .artifacts/검증 -Repeat 2 -IncludePreviousRelease
pwsh -NoProfile -File scripts/BuildPackage.ps1 -OutputDirectory .artifacts/패키지
```

[Verify.ps1](../scripts/Verify.ps1)은 NuGet 복원, Debug 및 Release 빌드·전체 테스트, Windows Publish 및 패키징을 순서대로 실행한다. 테스트별 TRX는 출력의 `TestResults/`에 남고 배포 후보는 `package/packages/`에 생성된다. [BuildPackage.ps1](../scripts/BuildPackage.ps1)은 패키징만 검사할 때 사용한다. 빌드 입력을 변경하면 새로운 커밋에 대한 검증이 필요하다. 로컬에서 GCP URL을 포함한 게시를 확인하려면 `LABPET_SERVER_URL`을 환경 변수로 제공한다.

## Actions와 태그

1. [검증 워크플로](../.github/workflows/verify.yml)는 `main` 푸시와 `main` 대상 PR에서 같은 스크립트를 실행한다. TRX는 실패가 발생한 실행에서도 업로드를 시도한다. 성공한 `main` 푸시 실행은 다음 단계의 입력으로 패키지와 검증 매니페스트를 30일 동안 보관한다. 운영 GCP 주소는 `main` 푸시의 게시 단계에 주입한다.
2. 검증 성공을 확인한 뒤 [Release.ps1](../scripts/Release.ps1)을 실행한다. 로컬 빌드 입력, 프로젝트 버전, 중복 태그, 최신 공개 릴리스, 패키지의 SHA256, 같은 커밋에서 성공한 `main`의 산출물을 검사한다. 사용자 승인에 따라 원격 `main`과 태그를 전송한다.
3. [릴리스 워크플로](../.github/workflows/release.yml)는 태그 푸시에서 해당 SHA의 성공한 `main` 검증 패키지를 다시 사용한다. 버전, 커밋, 실행과 시도 번호, CLI 버전, 각 파일 해시를 대조한다. 같은 저장소에서 동시에 한 릴리스만 공개한다.

```powershell
pwsh -NoProfile -File scripts/Release.ps1 -PackageDirectory .artifacts/검증/package/packages
git push origin refs/tags/vX.Y.Z
```

`vX.Y.Z`는 스크립트가 만든 버전으로 바꾼다.

## 파일과 배포 완료 조건

- 설치 프로그램 `LabPet-win-Setup.exe`, 포터블 ZIP `LabPet-win-Portable.zip`, 전체 업데이트 `LabPet-<버전>-full.nupkg`, `releases.win.json` 및 레거시 `RELEASES`가 필수다. 이전 공식 릴리스를 받아 차분 패키지를 생성할 수 있으면 `delta.nupkg`도 함께 올린다.
- 이전 파일 다운로드나 차분 생성·검증에 실패하면 앞서 격리해 만든 정상 전체 패키지와 그 피드를 사용한다.
- Actions는 초안을 만들고 모든 필수 파일을 업로드한다. 파일 개수, 크기 및 해시 검증을 마친 뒤 정식 릴리스를 공개한다. 공개 후 태그의 피드를 직접 내려받아 해시를 다시 확인한다.
- 배포 보고 전에 Actions의 성공, 정식 Release 페이지, 설치 파일, 포터블 파일, 전체 업데이트 파일과 `latest/download/releases.win.json`의 새 버전을 확인한다.

## 장애 복구

- 검증 실패 시 해당 테스트와 빌드 로그를 분석하고 [배포 장애 및 재발 방지](배포_장애_및_재발방지.md)를 갱신한다.
- 동일 태그와 커밋의 업로드 장애는 같은 Actions 실행을 재실행한다. 기존 초안은 최초의 검증 실행과 패키지에 묶이며, 검증된 동일 파일은 재사용한다. 아직 게시되지 않은 초안에서 전송 실패로 생성된 빈 자산만 다시 올린다. 검증 패키지가 보존 기간을 넘겼거나 초안 파일이 다른 경우 운영자가 먼저 해당 초안을 확인한다.
- 코드가 바뀌면 프로젝트 버전을 올리고 새 커밋과 태그로 검증한다. 공개 태그와 정상 릴리스는 보존한다. 동시에 여러 태그를 제출해 대기 실행이 취소된 경우 최신 릴리스 버전과 대기 태그의 순서를 확인한 뒤 실행한다.
- Windows 배포의 실패는 GCP 서버 재배포 사유가 아니다. 서버 코드나 서버 설정 자체가 바뀐 경우 서버 배포 절차를 사용한다. [GCP 클라우드 확장 가이드](07_GCP_클라우드_확장가이드.md)
