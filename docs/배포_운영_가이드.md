# Windows 클라이언트 배포 운영 가이드

## 표준화 기준

- Windows x64 환경과 [global.json](../global.json)에 고정된 `.NET SDK` 버전을 사용한다.
- 릴리스 버전(`Version`)과 Velopack 패키지 버전(`PackageReference Include="Velopack"`)은 [클라이언트 프로젝트](../src/LabPet.Client/LabPet.Client.csproj)에서 단일 관리한다.
- 패키지 ID(`LabPet`), 실행 파일(`LabPet.Client.exe`), 자동 업데이트 정적 피드(`https://github.com/DJU-ADAS-LAB/LabPet/releases/latest/download`), `%AppData%\LabPet\` 사용자 데이터 경로는 모든 릴리스에서 동일하게 유지한다.
- Windows 클라이언트 배포는 [GitHub Releases](https://github.com/DJU-ADAS-LAB/LabPet/releases)와 공식 Velopack CLI(`vpk`)를 사용하며, GCP SignalR 중계 서버는 별도로 운영한다. [GCP 서버 배포와 운영](../deploy/gcp/README.md)

## 로컬 검증

일반 검증은 `Release` 구성 빌드와 전체 테스트로 수행한다. [검증 워크플로](../.github/workflows/verify.yml)도 `main` Push 및 Pull Request에서 동일한 Release 빌드·테스트만 수행한다.

```powershell
dotnet restore LabPet.slnx
dotnet build LabPet.slnx -c Release --no-restore
dotnet test LabPet.slnx -c Release --no-build --no-restore --blame-hang-timeout 30s
```

Windows 패키징까지 로컬에서 점검할 때는 임시 출력 폴더를 지정해 `dotnet publish` 후 공식 `vpk` CLI로 확인한다(선택 사항).

```powershell
dotnet publish src/LabPet.Client/LabPet.Client.csproj -c Release -r win-x64 --self-contained true -o .artifacts/publish
vpk pack --runtime win-x64 -u LabPet -v <버전> -p .artifacts/publish -e LabPet.Client.exe -i src/LabPet.Client/Assets/app.ico -o .artifacts/releases
```

Windows x64 게시 후 [난독화 스크립트](../tools/obfuscation/Protect-LabPetRelease.ps1)를 실행한다. Obfuscar 2.2.50으로 지정한 클라이언트 메서드만 이름을 변경하며 변환된 DLL의 저장·게임·WPF 회귀 테스트 통과 후 Velopack을 실행한다.

## 단일 릴리스 워크플로 (`release.yml`)

실제 배포는 `v*.*.*` 태그 푸시 시 [릴리스 워크플로](../.github/workflows/release.yml) 단일 워크플로에서 수행한다. 커스텀 매니페스트, 워크플로 간 아티팩트 전달, 자체 GitHub REST API 업로드를 사용하지 않고 공식 `dotnet` + `vpk` CLI만으로 동작한다.

1. **버전·태그 일치 확인**: `LabPet.Client.csproj`의 `<Version>`과 `Velopack` 패키지 버전을 읽고, 푸시된 태그가 `v<Version>` 형식과 일치하는지 확인한다.
2. **Release 빌드 및 테스트**: `LabPet.slnx` 전체를 `-c Release`로 복원·빌드·테스트한다.
3. **Self-Contained 게시**: `win-x64` self-contained로 게시하고, 저장소 Secret/Variable `LABPET_SERVER_URL`이 설정된 경우 `-p:LabPetDefaultServerUrl=...`로 기본 GCP 중계 주소를 주입한다.
4. **이전 릴리스 다운로드 → 단일 `vpk pack`**:
   - `dotnet tool install -g vpk --version <velopack_version>`으로 프로젝트 NuGet과 동일한 버전의 `vpk` CLI를 설치한다.
   - `vpk download github --repoUrl https://github.com/DJU-ADAS-LAB/LabPet --token <github.token> --outputDir ./Releases`로 직전 공개 릴리스의 전체 패키지를 내려받는다.
   - `./Releases`를 대상으로 `vpk pack`을 **한 번만** 실행해 전체 패키지(`LabPet-<버전>-full.nupkg`), 차분 패키지(`LabPet-<버전>-delta.nupkg`), 설치 프로그램(`LabPet-win-Setup.exe`), 포터블 ZIP(`LabPet-win-Portable.zip`), 피드(`releases.win.json` · `RELEASES`)를 한 번의 과정에서 생성한다.
   - 이전 릴리스를 내려받지 못했거나 차분 생성 중 `vpk pack`이 실패한 경우에만 `./Releases`를 비운 뒤 `vpk pack`을 1회 재실행해 전체 업데이트 전용 패키지로 대체한다.
5. **GitHub Release 업로드 및 공개**:
   - `vpk upload github --repoUrl ... --token ... --outputDir ./Releases --publish --tag v<버전> --releaseName "LabPet v<버전>" --targetCommitish <sha>`로 초안에 현재 버전 자산을 업로드하고 `releases.win.json`·`RELEASES` 피드를 게시한 뒤 정식 공개한다.

## 릴리스 실행 절차 (사용자 승인 후)

1. [클라이언트 프로젝트](../src/LabPet.Client/LabPet.Client.csproj)의 `<Version>`을 올리고 `Release` 빌드·테스트를 통과시킨 뒤 `main`에 커밋·푸시한다.
2. 태그를 생성해 푸시한다.

```powershell
git tag -a vX.Y.Z -m "LabPet vX.Y.Z"
git push origin refs/tags/vX.Y.Z
```

3. 배포 완료 보고 전 다음 항목을 확인한다.
   - [릴리스 워크플로](../.github/workflows/release.yml) Actions 실행 성공
   - 공개 GitHub Release 페이지의 자산 6종(`LabPet-win-Setup.exe`, `LabPet-win-Portable.zip`, `LabPet-X.Y.Z-full.nupkg`, 차분 생성 시 `LabPet-X.Y.Z-delta.nupkg`, `releases.win.json`, `RELEASES`)
   - `https://github.com/DJU-ADAS-LAB/LabPet/releases/latest/download/releases.win.json`의 `Version` 일치 여부

## 장애 복구

- 테스트나 패키징 실패 시 원인과 로그를 분석하고 [배포 장애 및 재발 방지](배포_장애_및_재발방지.md)에 기록한다.
- 동일 태그·커밋에서 일시적 업로드 오류가 발생한 경우 GitHub Actions 실행을 재실행한다(이미 생성된 불완전 초안 자산이 있으면 삭제 후 재시도).
- 코드 변경이 필요한 경우 이미 공개된 태그는 보존하고 프로젝트 버전을 올린 새 커밋과 새 태그로 배포한다.
- Windows 클라이언트 배포와 GCP 서버 배포는 독립적이다. 서버 코드·설정이 바뀌지 않았다면 GCP 서버를 재배포하지 않는다. [GCP 클라우드 확장 가이드](07_GCP_클라우드_확장가이드.md)
